# DSH 0.1.5-rc.2 → 0.2.2-rc.2 — delta report for dsh-vscode

Durable artifact for the next platform upgrade. Answers one question: **what had to change in THIS repo
because of 0.1.5 → 0.2.2, where, and what is still a risk?** Every claim carries a `path:line` from the
vendored 0.2.2-rc.2 tree or from this repo.

Method: read the guides shipped at `vendor/node_modules/@deepseek-ai/dsh/docs/upgrade-guide/` (index +
`README.md`; 143 items in 13 version directories), the `dsh-doc` references
(`vendor/node_modules/@deepseek-ai/dsh-agent-preset/skills/dsh-doc/references/`), then verified each claim
against 0.2.2 code and cross-checked our repo (`src/extension.js`, `.smoke/`, `plugins/bundled/*`,
`plugins/presets/*`). Guide semantics: `v<T>/` describes the break when upgrading **from** `v<T>`.
Because we jump 0.1.5 → 0.2.2, every listed guide applies unless 0.2.2 code already satisfies it.

Baseline commit state: `vendor/node_modules` is a clean `@deepseek-ai/dsh@0.2.2-rc.2` install; this report
describes the tree as of the migration branch, where the work below is in place (see "Status" columns).

## 1. Web listener / auth / trust, and what the extension's proxy depends on

### 1.1 Service replacement: `webRuntime` → `webStartup`
- `web-startup` row provides the `webStartup` service (`dsh-web-app/lib/startup.js:19,61-68`); the Web patch
  mounts it at row id `web-startup` and reads flags from it (`dsh-web-app/cordis.patch.yml:172-173`).
- `web-runtime` is now the bundle's own glue plugin `@deepseek-ai/dsh-web-app`, not a service
  (`cordis.patch.yml:201-208`); `connection` reads `ctx.webStartup.trustedHosts`
  (`cordis.patch.yml:238-245`).
- Any overlay/profile patch still doing `inject: [webRuntime]` or `ctx.webRuntime.trustedHosts` fails to
  activate (guide `v0.2.1-alpha.1/web-listener-trust-config:11-33`).
- Our `--patch` overlay (`writeProfileOverlay`, `src/extension.js:995`) touches only `directory-picker*`
  rows and modlens families — it never names `webRuntime`/`web-runtime`. **No change needed.**

### 1.2 Wildcard listener rejection
- CLI rejects `--host 0.0.0.0`/`::` (`dsh-web-app/lib/startup.js:48`); the webserver config validates the
  same (`dsh-host-webserver/lib/index.js:155-157,304`).
- Web default is `host: !!js ctx.webStartup.host ?? '127.0.0.1'` (`dsh-web-app/cordis.patch.yml:187-188`).
- We pass only `--port` and `--no-open` (`src/extension.js:1597-1612`), so the default loopback bind
  applies. **No change needed.**

### 1.3 Index rendering now takes a `Peer`
- `renderIndex(html, peer)` / `collectIndexInjections(peer)`, and `webserver/index-inject` emits
  `(table, peer)` (`dsh-host-webserver/lib/index.js:646-659`).
- The static SPA seat calls `renderIndex(html, peer ?? ctx.connection.browserPeer)`
  (`dsh-host-frontend-static/lib/index.js:132`), so a file-level edit of `dist/index.html` still ships
  (it is read and re-injected at request time).
- Anything in this repo that injected index rows would break at call time; we have none — the clipboard
  shim is a `<script>` inside the file. Watch bundled host plugins on future upgrades for
  `renderIndex`/`index-inject` listeners.

### 1.4 The loopback reverse proxy still satisfies the 0.2.2 fence (why)
- Fence (`isTrustedApiRequest`, `dsh-client-connection/lib/index.js:240-250`): accepts a Host that is
  loopback (`127/8`, `localhost`, `::1`), **the listener bind IP on any port** (`:218-231`), or a declared
  trustedHost; rejects `sec-fetch-site: cross-site`; an `Origin`, when present, must equal the Host
  authority.
- Our proxy rewrites `Host` to `127.0.0.1:37750` (`forwardToHost`, `src/extension.js:484-548`; port is
  `DEFAULT_HOST_PORT`, `:265`), strips `sec-fetch-site`/cross-origin `origin`/`referer`
  (`:333-347`), and re-adds only same-origin browser markers (`sameOriginToApp`, `:319-327`).
  Loopback + same-authority origin ⇒ passes.
- Cookie binding is unchanged in kind: audience/name derive from the **Host header**
  (`requestAudience`, `:306-315`; `cookieName`, `:335-337`); the token→cookie 303 exchange still happens at
  `GET /?token=` (`:446-483`). `exchangeToken` presents the proxy authority as Host
  (`src/extension.js:456-481`), so the cookie it mints is bound to the same authority the proxy later
  presents. **The proxy needs no change for 0.2.2.**
- The host URL line we parse is unchanged: `dsh web: ${authenticatedUrl}` with
  `http://127.0.0.1:<port>/?token=…` (`dsh-web-app/lib/index.js:156-162`) still matches `URL_LINE`
  (`src/extension.js:48`).
- Client-plugin combo URL changed from root-relative to document-relative; `logClientSurface` already
  accepts both (`src/extension.js:409-440`, comment at :424-426). No action.

### 1.5 Clipboard shim (the one real casualty)
- 0.1.5 `dist/index.html` (git HEAD) carried the SPA-wide
  `navigator.clipboard.writeText` override with an `execCommand('copy')` fast path; the 0.2.2 file does not
  (`vendor/node_modules/@deepseek-ai/dsh-web-frontend/dist/index.html`, 21 lines, no script).
- Reason it is still needed in 0.2.2: first-party bundles migrated to a private copy helper, but bundled
  third-party clients still call `navigator.clipboard.writeText` directly
  (`.smoke/platform-patches/manifest.json:169-176`, e.g. `dsh-mnemon/lib/client.js`, memory-spaces client).
- Fix: stored patch `dsh-web-frontend/dist/index.html` in `.smoke/platform-patches/` (`manifest.json:153-178`),
  applied/verified by `python .smoke/platform-patches.py verify|apply`.

## 2. Plugin compatibility gate (`v0.2.1-alpha.3/plugin-engines-dsh`)

### 2.1 Exact rule (verified in code)
`evaluatePluginCompatibility` (`dsh-app-boot/lib/index.js:1075-1149`):
1. If the manifest has its **own** `engines.dsh` string, that range decides **alone**; `@deepseek-ai/dsh*`
   peers are ignored (`:1102-1108`).
2. Otherwise every `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` **peerDependency** range must match
   (`:1109-1121`). `workspace:^|~|*` in peers means the current runtime; `workspace:` inside `engines.dsh`
   is incompatible (`:1115-1119,1124-1127`).
3. Matching uses `semver.satisfies(runtimeVersion, range, { includePrerelease: true })` (`:1099-1101`), so a
   range like `^0.2.1-rc.0` or `>=0.2.1-rc.1 <0.3.0-0` **does** accept `0.2.2-rc.2` — prereleases count.
4. `runtimeVersion` is this `dsh-app-boot` package's `version` (`:1094-1098`), i.e. `0.2.2-rc.2` here — not
   the `dsh` CLI package.
5. Malformed `engines` / non-string `engines.dsh` makes the manifest *unreadable for compatibility* and the
   package is refused (`:1076-1078,1105-1106,1132`).

Two enforcement points: whole **profile bundles** are skipped at load (`loadProfileDirectory`,
`dsh-app-boot/lib/index.js:1800-1826`, collected in `skippedBundles`), and individual **rows** are denied by
`prepareProfileEntries` → `preflight` (`:3096-3178`), which sets `disabled: true` and writes
`dsh: disabling profile plugin …` to stderr. Profile startup uses the same preflight for preset child
rows (`dsh-agent-preset-registry/lib/index.js:226`), so a preset row and a profile row are equally gated.

### 2.2 Sanctioned exemption mechanism
- File: `<profile>/compatibility.json` (`PROFILE_COMPATIBILITY_FILENAME`,
  `dsh-app-boot/lib/index.js:1164`), format `{ "<name>@<exact-version>": ["<exact DSH version>", …] }`
  (`readProfileCompatibility`, `:1188-1239`). Keys must be canonical exact SemVer; invalid records are
  ignored with a warning, never fatal (`:1219-1238`).
- Writer: `setProfileVersionExemption` (`:1257-1269`) — exact versions only, `acceptRisk` required to
  grant, target runtime must be the running one (`:1259-1261`).
- CLI surface: `dsh plugin allow-version|revoke-version|version-exemptions <pkg@ver> --dsh-version <exact>`
  (`dsh/lib/plugin-DC80YBt4.js:17-49`), plus the plugin-manager UI.
- **Is writing `compatibility.json` ourselves the documented path?** Guides only name
  `dsh plugin allow-version` / the plugin manager (`v0.2.1-alpha.3/plugin-engines-dsh:18-21`;
  `pluginCompatibilityWarning`, `dsh-app-boot/lib/index.js:1156-1159`). The file format is fully specified
  in code and the reader tolerates a hand-written file, so seeding it is legitimate for an embedded
  deployment that cannot run the CLI — but it is **undocumented**. This repo does exactly that, defensively:
  `writeCompatibilityExemptions` (`src/extension.js:1525-1563`) writes only exact shipped
  `name@version` records, only for `BUNDLED_PLUGINS`, only when baked plugins are enabled, never a wildcard,
  and prunes records of retired plugins; the table is empty today (`PLUGIN_VERSION_EXEMPTIONS`,
  `src/extension.js:1501`).

## 3. Presets: 0.2.2 declaration model and this repo's migration

### 3.1 Model
- A preset is one Loader row: `name: '@deepseek-ai/dsh-agent-preset'`, `config: {id, name?, description?,
  order?, plugins: [entry list]}` (`dsh-agent-preset/lib/index.js:13-19`).
- `plugins` is an ordinary Cordis entry list: `id`, `name`, `config`, `disabled`, `group: true` +
  `isolate` realms, `!!js` expressions (`dsh-doc/references/composition-reference.md:6-19`).
- Group marker preserves child `!!js` expressions until the children activate
  (`dsh-agent-preset/lib/index.js:11-12`).
- Shipped Web presets live in the `dsh-web-app` bundle (`presets/{standard,ptc,minimal,cordis}.patch.yml`,
  listed in `dsh-web-app/package.json` → `dsh.bundle.patch`); `standard` is the roster default
  (`dsh-web-app/cordis.patch.yml:616-620`).
- Editing a shipped preset = override the whole declaration row (`compositions.md:49-61`); a patch replaces
  the matched row's whole `config`.

### 3.2 Relative child names — the trap
- Docs: "inserted relative paths are anchored beside their patch file"
  (`composition-reference.md:13`), implemented by `anchorInsertedPluginNames`, which visits **`patch.insert`
  rows and nested `group: true` configs only** (`dsh-app-boot/lib/index.js:4737-4746`).
- A preset declaration is not `group: true`, so **its `config.plugins` relative names are not anchored**;
  the registry mounts the child tree with the recorded tree base URL
  (`dsh-agent-preset-registry/lib/index.js:219-226,486-517`), which is the profile config directory
  ("Relative entry names resolve against the config directory", `dsh-app-boot/lib/index.js:5250-5251`).
  A `./x.mjs` in `config.plugins` therefore resolves to `<profile>/x.mjs` and fails.
- Sanctioned alternative: "Resolve assets from installed packages rather than a preset directory"
  (`compositions.md:75`). This repo packages each entry module as a real package under `plugins/bundled/`
  (`transplantBundledPlugins` copies every directory under `plugins/bundled/` into the profile's
  `node_modules`, `src/extension.js:1391-1475`), and the presets name the package
  (`dsh-preset-router-standard-bootstrap`, `dsh-preset-router-standard-gitbash`,
  `dsh-preset-router-spec-bootstrap`). Each package carries the preset's whole `.mjs` set with `main`
  pointing at the entry file, so the entry's `./router-core-*.mjs` import resolves inside the package.
  Generated by `.smoke/gen-presets.py` (refuses to run if a preset still contains `name: ./…`).

## 4. Persistence / session format, and the platform-patch baseline

### 4.1 0.2.2 facts
- `dsh-session-persistence-jsonl` is a **function plugin** with named exports and no default

## 9. MCP: the official manager owns the plane; `dsh-mcp` retired

- 0.2.2 `dsh-web-app` mounts the official manager: row `mcp-manager`, `@deepseek-ai/dsh-mcp-manager`,
  `inject: [credentials]` (`dsh-web-app/cordis.patch.yml:149-155`). It manages a fleet of
  `dsh-mcp-client` instances, exposes `ctx.mcpManager`, Remote status/restart/probe/watch, and a Settings
  page; documented limitations: no OAuth browser flow, no per-server tool allow/deny, no management surface
  beyond Settings (`dsh-mcp-manager/README.md:10-33,172-180`).
- **Decision for this build: `dsh-mcp` is RETIRED.** It was removed from `BUNDLED_PLUGINS` (its rationale
  comment stays where the package used to be listed, `src/extension.js:733-742`) and added to
  `RETIRED_PLUGINS` (`src/extension.js:816-823`), so `syncBakedPlugins` prunes any stale profile entry and
  transplanted tree, and `plugins/bundled/dsh-mcp/` is deleted. The official `mcp-manager` row stays
  **enabled** and owns the plane (Settings → MCP, `mcp` settings namespace, `${credential:REF}` templates).
- Why the substitution was abandoned (the interesting part): both halves fit the host, but the **client**
  halves collide. `dsh-mcp` 1.15.1's client half self-mounts a Remote contribution in namespace
  `mcpManager`, while 0.2.2's `dsh-api-remotes` client statically imports and mounts the official
  contribution for the same namespace (`dsh-api-remotes/lib/types/client/index.js:15,45`; mount loop
  `:39-52`). Every client mount is serialized through the client gateway's mutation queue
  (`dsh-api-gateway/lib/types/client/index.js:88-116`: `$mount` → `enqueue`, a promise chain), so the two
  mounts deadlock it. Symptom found by CDP against a **real browser**, not by boot tests: the panel hangs on
  "Loading plugins…" at ~40% of client plugins, the `api-remotes` fiber stays `LOADING` forever after
  productAnalytics/agentPresets/commands/agentTeams, and there are 0 console errors; skipping only that
  `$mount` restores a full UI. Host-side boot tests cannot see this — the failure is purely client-side.
- Product cost accepted with the retire: the old MCP management page, its OAuth flow, and
  `mcp_tool_search` hot-injection are gone; the official manager documents those as Known Limitations
  (`dsh-mcp-manager/README.md:172-180`).
- Do **not** re-add `dsh-mcp` as a bundle while the official `mcp-manager` is mounted: one namespace, two
  client mounts, same deadlock. Re-introduction requires dropping one of the two client contributions (or
  keeping the plugin host-only) and restoring its dependencies (see §11.3).

## 11. Remaining risks / open items

1. **Node runtime (highest).** `@deepseek-ai/dsh` requires Node ≥24.9, but the extension boots the host with
   VS Code's Electron Node (`process.execPath` + `ELECTRON_RUN_AS_NODE=1`, `src/extension.js:1597-1660`).
   No runtime guard exists in `dsh/lib/**`, so it runs; if a 0.2.x patch starts using a Node-24-only API or a
   guard is added, the panel would stop booting. Options: ship a Node 24 runtime in the vsix, or pin/verify
   the VS Code Electron Node version at activation and surface a clear error.
2. **`webRuntime`/`ctx.menus` in user branches.** Any user `--patch`/profile overlay still naming
   `webRuntime`, `ctx.webStartup.*` misuse, `dsh-tools.mode`, or `ctx.menus` fails or is ignored silently.
   There is no migration detection in the extension today.
3. **MCP plane is the official manager; `dsh-mcp` is retired** (§9). Its client half collided with the
   official `mcpManager` Remote namespace and deadlocked the client gateway's serialized mount queue — a
   real-browser-only failure that boot tests cannot detect. Consequence: `plugins/bundled/_hostdeps` loses
   the `@modelcontextprotocol/*` + `js-yaml` closure (the dependency set only `dsh-mcp` required); a future
   re-introduction of `dsh-mcp` must restore those deps **and** fix the one-namespace/two-mounts collision
   first.
4. **One-way session upgrades.** 0.2.2 writes format v3/v4 logs and `subagent/catalog` payload v3; a downgrade
   to 0.1.5 cannot open those Sessions (`v0.2.2-alpha.3/subagent-names:18,27`). Do not ship a downgrade path
   without a warning + backup.
5. **Preset bundle packaging** (`@dsh-vscode/presets` + `dsh-preset-*`) relies on
   `transplantBundledPlugins` copying **every** directory under `plugins/bundled/` into the profile
   `node_modules` (`src/extension.js:1391-1475`). If that is ever narrowed to `BUNDLED_PLUGINS`, the bare
   package names used by preset children stop resolving.
6. **`ppt-master` declaration ownership** (§0 #9): once the package patch is emptied, `dsh-ppt-master` remains
   only as the plugin mounted by row `ppt-master-tools`; do not re-add its declaration patch or activation
   fails with `Duplicate agent preset: ppt-master`.
7. **Compatibility gate drift.** Bundled plugin manifests are third-party and can start declaring exact
   `engines.dsh`; the gate then refuses them silently at bundle level. Re-run the §2.3 audit each upgrade and
   add exact exemptions via `PLUGIN_VERSION_EXEMPTIONS` only after boot-verifying the plugin.
