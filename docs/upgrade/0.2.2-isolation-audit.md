# Isolation audit: does the 0.2.2 platform touch DSH NEXT?

Date: 2026-11-14. Scope: the VS Code extension (0.4.2, bundled `@deepseek-ai/dsh`
0.2.2-rc.2) and the 14 bundled ecosystem plugins it ships. Question: can anything
in this extension read, write, delete, kill, or otherwise disturb a second DSH
installation on the same machine — specifically the DSH NEXT desktop app
(`~/.dsh`, `%APPDATA%\DSH Desktop`, the app install dir) and its sessions,
credentials, and profile?

## Method

Two independent angles, because either one alone is weak.

1. **Static**: every `~/.dsh`-ish literal and every `homedir()` use in
   `src/extension.js` and in the bundled plugins' host-side entry points, plus
   every child-process and network call the extension makes.
2. **Runtime**: the vendored host is booted under an `fs`/`child_process`
   preload (`.tmp-vendor/fs-audit.cjs`, loaded with
   `NODE_OPTIONS=--require=…`) that records every write-ish call
   (`writeFileSync`, `mkdirSync`, `rmSync`, `unlinkSync`, `renameSync`,
   `copyFileSync`, `cpSync`, `openSync('w')`, streams, their `fs.promises`
   twins, `spawn`/`exec`/`fork`, `process.kill`) as
   `<pid>\t<op>\t<path>`. With `DSH_FS_AUDIT_READS=1` it also records reads,
   stats, and `readdir` on the paths that would matter (`~/.dsh`, `~/.mnemon`,
   `DSH Desktop`, `DSH NEXT`, `.credentials`, `~/.claude`, `~/.codex`, `~/.pi`,
   `~/.ssh`), while ignoring reads inside the probe home.
   Node's named builtin bindings are live, so ESM code (`import { writeFileSync }
   from 'node:fs'`) is intercepted as well.

   The probe (`.tmp-vendor/fs-probe.mjs`) transplants `plugins/bundled` into a
   throwaway profile the same way `syncBakedPlugins()` does, writes the same
   profile manifest / `compatibility.json` / overlay, spawns
   `dsh --profile web --patch … --port 0 --no-open` with the extension's exact
   environment (`DSH_HOME`, `DSH_EMBEDDED`, `DSH_DOCTOR_HOME`,
   `DSH_PROXY_PORT`, `MNEMON_CLI_PATH`), waits for the ready line, fetches `/`
   once, waits 6 s, and stops the tree with `taskkill /PID <pid> /T /F` — the
   extension's own shutdown path.

## Result

Two runs (transplant + boot, then a `--keep` re-run with read auditing). Host
booted both times (`dsh web: http://127.0.0.1:<port>/?token=…`, GET `/` → 303),
all 14 bundled plugins loaded, no plugin import failure.

Writes and deletes outside the extension's own `DSH_HOME`:

| Target | Writes/deletes |
| --- | --- |
| `C:\Users\li554\.dsh` (desktop home: sessions, `workspace.json`, `.credentials.yaml`) | **0** |
| `%APPDATA%\DSH Desktop` (health snapshots, recovery) | **0** |
| `…\Programs\DSH NEXT` (app install, `app.asar`) | **0** |
| VS Code `globalStorage` of other publishers | 0 (the legacy-home migration only *copies from* `your-publisher-id.dsh-vscode`, never deletes) |
| `%TEMP%\dsh-<id>\**` | platform scratch: materialized `diagnose-windows-sandbox-acl` skill, `dsh-spill-*`, `dsh-hmr-clock-*`, `dsh-ssh-uploads` |
| `C:\Users\li554\.mnemon\**` | mnemon plugin: creates `runtime/` and takes `.memories.lock` |

Reads of the sensitive paths above: **0** — the host does not even `stat`
`~/.dsh`, so the isolation is not merely "the write was denied".

Every other write landed inside the probe `DSH_HOME`
(`profiles/web/cordis.yml`, `storages/workspace.json`, `.credentials.yaml`,
`router-standard/*`, `.anonymous-user-id`), i.e. the same set the real extension
writes under its VS Code `globalStorage` home.

Processes: no `spawn`/`kill` of anything outside the host's own tree; shutdown is
`taskkill` on the child pid the extension itself created. Network: proxy binds
`127.0.0.1:37750` (extension default, idle on this machine), the host binds
`--port 0` — never `0.0.0.0`. Environment: `DSH_HOME`/`DSH_EMBEDDED`/… are only
overrides in the child's `env`; no `setx`, registry, or global npm.

## The one user-level store: `~/.mnemon`

mnemon's storage root is `process.env.MNEMON_DATA_DIR || "~/.mnemon"`
(`plugins/bundled/dsh-mnemon/lib/index.js:1004-1006`, default
`storageScope: "global"`). The extension does not set `MNEMON_DATA_DIR`, so its
memories (`runtime/memories.json`, `MEMORY.md`, `USER.md`, `sources/`, `documents/`)
live in the user's home, outside the extension's `DSH_HOME`. That is the only
path this extension writes that another DSH install could also use.

Today it is harmless: `C:\…\DSH NEXT\resources\app.asar` (237 MB) contains no
`.mnemon` reference at all, and the desktop profile's dependencies do not include
mnemon. If mnemon is ever installed into the desktop app, both harnesses would
share one memory store and serialize on the same `.memories.lock` (stale
takeover after 30 s) — no corruption, but memories written in one would surface
in the other.

Hardening option (not applied): pass `MNEMON_DATA_DIR=<home>/mnemon` in the
host's spawn env, which keeps the extension's memories inside its own home; the
existing `~/.mnemon` content would need a one-time import if it should be kept.

`~/.modlens/**` (modlens's own config/state) and on-demand reads of other
agents' transcript stores (`~/.claude`, `~/.codex`, `~/.pi`) are the same kind of
user-level, by-design side effect; neither appeared during boot.

## Reproduce

```powershell
node .tmp-vendor/fs-probe.mjs            # full transplant + boot + write audit
node .tmp-vendor/fs-probe.mjs --keep     # reuse profile, also audit reads
Get-Content .tmp-vendor/fs-probe/report.txt
```

Checks live in the repo only (`.tmp-vendor/` is gitignored by design).
